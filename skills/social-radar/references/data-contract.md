# Local record contract and commands

Node.js 18+; no runtime dependencies. Commands below use a checkout-relative script path; an installed copy lives at `~/.codex/skills/social-radar/scripts/` (or `$CODEX_HOME/skills/social-radar/scripts/`). Keep the store outside the installed skill/package and out of git.

```text
outputs/social-radar/
  events/                 append-only, ordered JSON events (never edit)
  materials/<work-key>/   caption.md, capture inputs, originals and text sources
  drafts/<work-key>/<rev>/ brief.md, script.md, evidence.md
  reports/<run>/          report.html, tracking.csv, snapshot.json
```

Each append rereads the journal and each status/render rehashes every registered file, so cost grows with the store; with original videos, hashing media bytes dominates status/render time, while `summary` skips hashing. At the default pace (two 50-work rounds a day) a store gains roughly 300 events a day; around 10,000 events each append takes a few seconds. For long-running use, start a new store directory each month (for example `outputs/social-radar/2026-10/`) or once `summary` becomes slow, and keep older stores read-only for reference. Carry active watchlist works into the new store by capturing them again; never copy journal files between stores. Before switching, run `summary` in the old store to list decisions and pending tasks. In the new store, re-record the user's earlier decisions with their original `userRequest` text and recreate needed revisits against fresh baselines. Newness restarts per store, so check the old store before calling a work new.

Every event has a stable `id` (letters/digits/dot/underscore/hyphen, max 120), `type` and timezone-qualified `recordedAt` (actual save time). New save times cannot precede the preceding committed event or run more than five minutes ahead of the machine clock, since a mistyped future time would otherwise block every real save; a later-saved backfill retains its older `capturedAt`/`sampledAt`. Dates must exist in the Gregorian calendar, with hours 00–23 and minutes/seconds 00–59; impossible dates are rejected rather than normalized. Seconds are required; fractions may have up to nine digits. Repeating the same ID and content is a no-op, even when it omits helper-filled hashes or its referenced files changed later; changing it is rejected. The ledger embeds hashes for registered files. New reads/corrections use new event IDs and asset paths. Only the collector writes; offline readers submit payloads to it. `events/` is authoritative; reports are regenerable views. `.writer.lock` and `events/` (including normalized or resolved symlink aliases) are reserved and cannot be registered as assets or drafts. Do not edit journal files, old assets or registered drafts.

```bash
node skills/social-radar/scripts/radar.cjs append --store outputs/social-radar --input capture.json
node skills/social-radar/scripts/radar.cjs summary --store outputs/social-radar
node skills/social-radar/scripts/radar.cjs status --store outputs/social-radar
node skills/social-radar/scripts/radar.cjs render --store outputs/social-radar --out outputs/social-radar/reports/latest
```

`summary` prints a compact view for resuming work: the five latest rounds, pending tasks, shortlisted works reviewed in the past seven days (with a count of older ones), decisions, gap counts and integrity issues. For speed it checks only that registered files are present and nonempty; `status` and `render` also verify every hash; `status` prints the full snapshot and `render` writes it to `snapshot.json`. Agents resuming work should read `summary`; redirect `status` to a file when the full snapshot is needed. `summary`, `status` and `render` optionally accept `--now <ISO-time>` for reproducible inspection. The CSV opens in Excel, protects formula-leading text and carries the user's latest decision next to the review recommendation (or `latest review unsupported` when the newest review lost support); its gaps column lists the latest substantive capture's gaps with review and integrity gaps, and `earlier_capture_gaps` keeps other captures' gaps not repeated there; cards show the capture day next to relative date labels; it is an export, not an editable database or XLSX workbook. Dashboard buttons prepare instructions using only a validated work ID and the store path; public titles/authors are not interpolated into commands. They provide clipboard/manual-copy fallback and do not mutate records or claim to have run a task. Use a new report directory to retain past reports. 今日选题 lists shortlisted works whose latest review is from the past seven days, newest first; older candidates fold into a collapsed group, and selected works move to their own list with draft links. Before writing any report file, the renderer rejects symbolic-link output targets (including dangling links), target aliases and paths or file identities that overlap registered assets, drafts or journal files. Material previews, review evidence links and CSV file links use first-owner assets; excluded legacy review links carry a warning and raw legacy records remain in the snapshot history.

Appending verifies the registered files an event cites directly and a revisit's baseline evidence. Reviews, drafts and round completion are judged on the work's or round's intact files, as status does, so an unrelated lost file does not block them. Completed rounds count only captures whose files are intact, so a replacement capture can complete a round after an original file is lost, and completed revisits require an intact due-time observation. Unrelated historical files may be missing or empty without blocking replacement captures under new paths or other intact evidence. `status` and `render` run the full integrity pass without failing (`summary` checks presence only): each missing, emptied or changed registered file is listed in `integrityIssues` (also in HTML, CSV and a stderr warning) and excluded from materials, eligibility, observations, reviews and drafts. Excluded files keep their ownership and history: a lost file still owns its content, and a work read with it still counts as previously read. Registered files are never edited in place. To revise a draft, save new files and register a new draft revision; to replace lost material, capture it again under a new path.

Report directories cannot be `events/` or any descendant, including directory symlink/junction aliases. This check runs before creating directories so an event-shaped output directory cannot corrupt the journal namespace.

The journal directory itself must resolve strictly beneath the selected store before it is listed, loaded, created or written. An `events/` symlink/junction to another store or an external directory is rejected; a contained directory alias may still be used.

Event-shaped journal entries must be regular files. Symbolic links and directories are rejected before event contents are read, even when their names match the journal pattern.

Registration and full integrity checks also reject files inside the resolved journal directory and compare hard-linked file identities against journal files and the active writer lock. A hard link under `materials/` or a draft directory does not make an internal ledger file usable as evidence or a document.

## Events

Below are schema examples, **not real observations**. Replace all sample identifiers, times and material paths with actual captured values. Asset files must exist and be nonempty before `append`.

### Round and attempts

```json
{
  "id": "round-20261021-am", "type": "round_started", "recordedAt": "2026-10-21T09:00:00+08:00",
  "roundId": "20261021-am", "timezone": "Asia/Taipei",
  "profile": "AI、科学、数学；希望有具体例子、独立观点及可复现方法",
  "config": {"targets": {"douyin": 25, "xiaohongshu": 25}}
}
```

Default config: `minNew:35`, `minRecommended:15` per active platform, `practicalSlots:10`, `minIntervalMinutes:20`, `shortWindowHours:6`, `lowFollowerCeiling:5000`, `lowLikeCeiling:1000`, `minNewLikes:10`, `minRelativeGrowth:0.5`, `fastLikesPerHour:100`, `accelerationRatio:2`. These are configurable working heuristics, not predictions. For a focused run also lower `minNew`, `minRecommended` and `practicalSlots` explicitly; they do not silently scale with targets.

When supplied, `config.targets` must be a non-array object. Null, primitives and arrays are rejected before defaults are merged; omitted targets or omitted individual platform keys retain their defaults. Coverage minimums must be reachable: `minNew` and `practicalSlots` cannot exceed the combined target, and `minRecommended` cannot exceed any active platform's target.

An `attempt` adds `roundId`, `attemptId`, `status` (`running`, `paused`, `partial`, `completed`), `reason` and optional affected `platform`. A continuation reuses `roundId` with a new `attemptId`. `completed` is rejected until count and configured coverage are met. Counts remain derived from evidence, even if an attempt is marked paused/partial. Store each interruption and completion as its own event; do not modify the start event.

### Capture

```json
{
  "id": "capture-example-01", "type": "capture", "recordedAt": "2026-10-21T09:05:10+08:00", "roundId": "20261021-am",
  "work": {"id": "xiaohongshu:example", "platform": "xiaohongshu", "url": "https://www.xiaohongshu.com/explore/example", "title": "示例标题", "author": "示例作者", "dateKind": "unknown", "dateLabel": "昨天", "publishedAt": null},
  "route": "recommendation", "practicalMethod": true,
  "readKinds": ["caption_body", "image_text"], "coverage": "原页正文和第1页已读；总共3页", "gaps": ["第2–3页待补"],
  "assets": [
    {"kind": "caption", "path": "materials/xhs-example/caption.md", "sourceUrl": "https://www.xiaohongshu.com/explore/example", "capturedAt": "2026-10-21T09:04:51+08:00", "coverage": "作者标题与正文"},
    {"kind": "page_screenshot", "path": "materials/xhs-example/page-01.png", "sourceUrl": "https://www.xiaohongshu.com/explore/example", "capturedAt": "2026-10-21T09:04:52+08:00", "coverage": "实际作品页，作者、内容及互动栏", "metrics": {"likes": {"value": 17, "raw": "17", "precision": "exact"}, "favorites": {"value": null, "raw": "1.1万", "precision": "rounded"}}}
  ]
}
```

`work.id` is platform plus native ID; preserve it across all rounds. Once a capture records `work.authorUrl`, later captures may repeat or omit it but cannot name a different profile. Profiles compare by platform user ID, so changing query parameters such as `xsec_token` are accepted. The displayed `author` name may be corrected. A confirmed `publishedAt` likewise persists when a later capture omits it and still applies to that capture's evidence; a later capture may revise it only to a time no later than any work evidence. `work.url` must be a canonical URL on the matching platform and contain that same native ID: Douyin `/video/<id>` or `/note/<id>`, Xiaohongshu `/explore/<id>` or `/discovery/item/<id>` (with or without `www`). Resolve short/share links to that canonical URL before saving; tracking query parameters are allowed. `dateKind` is `published`, `edited` or `unknown`; only a confirmed original publication date sets `publishedAt`. Capture routes: `recommendation`, `related`, `search`, `direct`. `readKinds`: `caption_body` (substantive body, not title), `image_text`, `video_fragment`, `original_subtitles`, `verified_transcript`; an empty array is a saved lead, not a counted read. Eligible captures require a substantive read, caption asset and real page screenshot/video/clip from the work itself; an author-profile follower screenshot cannot fill the page or read roles. Counts use unique works; repeated reads and newness are shown separately. A lead discovered earlier only becomes previously read after eligible evidence is saved. Newness follows round order: an eligible capture backfilled into an earlier round counts as a previous read for later rounds even when saved afterwards. A later round counts a work only when that round saves new page screenshot, video or clip evidence for it; re-listing files registered in an earlier round is not a new read. Route coverage counts a work when any capture of it in that round, other than a metrics-only revisit capture, came from recommendations or related posts, so a lead found there and read later still counts.

Asset kinds: `caption`, `page_screenshot`, `original_image`, `video`, `clip`, `frame`, `original_subtitles`, `transcript_candidate`, `platform_summary`, `image_text`, `comments`, `source_comments`, `source_page`, `source_image`, `research_note`, `metric_snapshot`. Every asset has a store-relative `path`, `sourceUrl`, `capturedAt`, `coverage`; the helper adds/verifies `sha256`. A registered file belongs to its first work and cannot be reused for another work, including normalized path aliases, symlinks and hard links across captures. Save a separate file for each work. Registered files retain both their original bytes and metadata, including capture time and metric readings. Reusing a file for the same work cannot change that metadata. Legacy reuse remains in history but cannot supply a different work or relabelled observation evidence; `status` and `render` resolve file identities when checking it.

A capture cannot list one file more than once, even through dot-segment aliases, symlinks or hard links. Identical bytes count as the same evidence: the first registration of a SHA-256 owns it. A byte-identical copy of a page screenshot or metric snapshot cannot be registered for another work. A reposted identical original image, video, clip or frame may be saved for another work but never counts as its evidence. Captions, OCR text, subtitles, transcripts, comments and external sources may repeat across works; a byte-identical metric file is accepted only at the original `capturedAt`, as in the correction flow; and captured assets and registered drafts cannot share content. One capture cannot list the same media or metric content twice. Round counts and new substantive reviews use resolved, first-owner assets with their original metadata. Duplicate or unowned legacy registrations cannot supply the required caption and page/video roles; keep that history and save a new valid capture.

Every declared read kind requires compatible saved evidence from the work itself: `caption_body` needs a caption; `image_text` needs an original image, saved image text or a page screenshot; `video_fragment` needs a video/clip; `original_subtitles` needs original subtitles; `verified_transcript` needs a verified transcript candidate. Legacy captures lacking the declared material do not qualify for quotas or new reviews. Confirmed publication timestamps cannot be later than the capture event or any work-page/media evidence saved for that work, including earlier captures. Older external sources and author-profile evidence are allowed because they do not depict the tracked work itself.

Work-bound asset `sourceUrl` values must identify the same platform/native work as `work.id`; a new copy of another work's screenshot cannot qualify it. Explicit `source_page`, `source_image`, `source_comments` and `research_note` assets may cite external public sources. Use `source_comments` for discussion of an X original or another source, keeping `comments` for the tracked work's own comments; a review comment's platform must match its saved comment source. For homepage follower samples, save the verified creator profile as optional `work.authorUrl` (`/user/<id>` on Douyin, `/user/profile/<id>` on Xiaohongshu). A screenshot or metric snapshot containing only `followers` may use that exact profile URL; other work-bound assets still need the work URL. The collector verifies that the profile belongs to the work's author.

Only `page_screenshot` and `metric_snapshot` assets can supply observation metrics. A `metric_snapshot` is the saved visible-page/DOM reading, including the displayed labels, values, page identity and the sampling time, not a reconstructed researcher summary. Recording the time makes an unchanged count produce a distinct file. Each metric-bearing asset has a `metrics` object with the exact same value/raw/precision schema as observations. Metric snapshots require it; screenshots used only for content do not. Readings must actually be visible in that asset. `capturedAt` is the actual screenshot/snapshot instant; do not backdate it or relabel an old capture to match a desired sample time.

A `clip` also needs actual `startSeconds`/`endSeconds`. A `transcript_candidate` needs `status: ai_extracted_unverified|partial|verified`; `verified_transcript` reading requires a verified transcript asset. `verified` is an agent attestation backed by comparison to original audio/subtitles, not a helper-generated guarantee. Detailed page/interval annotations belong in the pack's capture JSON and `coverage` text.

### Observation

```json
{
  "id": "obs-example-01", "type": "observation", "recordedAt": "2026-10-21T09:06:00+08:00", "roundId": "20261021-am", "workId": "xiaohongshu:example",
  "sampledAt": "2026-10-21T09:04:52+08:00", "evidencePaths": ["materials/xhs-example/page-01.png"],
  "metrics": {"likes": {"value": 17, "raw": "17", "precision": "exact"}, "favorites": {"value": null, "raw": "1.1万", "precision": "rounded"}}
}
```

Supported public metrics: `likes`, `favorites`, `comments`, `shares`, `followers`. Each uses `value`, literal `raw` count and `precision: exact|rounded|unavailable`. Unknown/rounded numeric values are null. Rounded readings require a nonempty visible display; use `unavailable` when nothing was shown. Exact displays accept integers and comma grouping; keep labels separately in evidence. A homepage follower reading at another time gets its own observation. The latest available reading is tracked separately per metric; an unavailable later reading does not erase earlier data or refresh its timestamp. If the later value is rounded, show it as rounded rather than reusing an older exact number.

Every `evidencePaths` entry must be a saved metric-bearing screenshot/snapshot for this work, captured at the same instant as `sampledAt` (equivalent timezone offsets are accepted) and first registered in the observation's `roundId`. Re-registering an old asset in another round does not transfer its sampling round. Each observation metric must match at least one referenced asset's reading; multiple referenced readings for that metric must agree. A caption, screenshot without metrics, stale capture, wrong round or mismatched count is rejected. For a fresh revisit, save fresh evidence before appending the observation. Do not include unrelated content assets in observation evidence.

To correct a mistaken reading, register a copy of the original screenshot or snapshot under a new path with the same `capturedAt` and the `metrics` that evidence actually shows, then append a new observation with `correctsObservationId` naming the mistaken one. The correction shares its work, round and `sampledAt` and restates every metric of the corrected observation. The corrected observation stays in the ledger, is listed in `correctedObservations`, and no longer feeds latest metrics, growth or revisit completion. Correct a correction by naming the latest one. Without `correctsObservationId`, a second reading of the same metric at the same instant is rejected. A corrected observation stays excluded even if its correction later loses its evidence, and a new revisit task cannot use it as a baseline.

Legacy observations lacking this binding are preserved in the ledger but excluded from latest metrics and growth. `snapshot.json` exposes per-work `evidenceGaps`, also shown in HTML and CSV. Such observations cannot serve as revisit baselines or satisfy revisit completion. Replaying an unchanged legacy observation is a no-op, not a new endorsement; collect a new sample instead of changing old timestamps/values to repair it.

Growth compares the latest available like observation with the most recent one at least `minIntervalMinutes` earlier by **sampling** time, or with the previous one when none is that old, so an extra nearby reading does not erase a measured window. Both must be exact, at least `minIntervalMinutes` apart and at most `shortWindowHours` apart to flag short-term growth. Shorter windows retain delta but no hourly rate; longer ones display a cross-round average without short-term flags. Decreases are flagged, never converted to growth. Rounded intermediate samples break exact comparison. Zero-to-positive changes have null relative percentage, not infinity. Acceleration compares that window with the preceding window built the same way and needs a positive earlier speed; a zero earlier speed is not an infinite acceleration claim. The chart always preserves the original points and times.

Growth thresholds come from the round of the latest valid, available like sample; the low-follower threshold separately comes from the round of the latest available follower sample. Content-only captures, old-round backfills and unavailable readings do not select a new metric configuration.

### Review

A `review` adds `workId`, `captureIds` (saved captures actually read), `summary`, `opportunity`, `angle`, `recommendation: shortlist|watch|archive`, `evidencePaths` and arrays:

- `gaps`: remaining missing material/verification.
- `sourceRefs`: `{url, status: exact|account_clue|unverified, note}`. An `exact` reference requires a registered `source_page`, `source_image` or `research_note` with the same `sourceUrl`, cited in the review's `evidencePaths`. Store original text/translation in assets, and explain source clusters in `note`.
- `claims`: `{text, status: verified|author_report|inference|unresolved, evidencePaths}`. Evidence paths refer to captured assets, including primary-source checks saved as research notes. A `verified` claim must cite at least one `research_note`, `source_page` or `source_image`; a caption or other self-report supports only `author_report`.
- `comments`: `{platform: douyin|xiaohongshu|x, kind: disagreement|request|meme|support|ai|other, sampledCount, summary, evidencePaths}`. Empty means no verified discussion, not zero total comments. The detailed reply structure lives in the comments asset.

All referenced evidence must already be registered for that work. At least one referenced `captureIds` entry must be an eligible substantive read with both a caption and page screenshot/video/clip; unreferenced reads do not qualify a title-only lead. Each comment summary must reference at least one asset of kind `comments` or `source_comments` on its stated platform; additional screenshots or caption context are allowed but cannot replace the saved comments. Reader payloads are proposed reviews; the collector reconciles them and appends them. The latest valid review drives the report; all older reviews remain.

Historical reviews are checked against the same ownership, provenance and substantive-read rules before becoming current. The latest valid review drives recommendations and drafts, but when the newest review has lost support the work leaves today's shortlist until a new review is recorded rather than promoting an older one; unsupported revisions remain in `reviews` history with `reviewGaps` shown in HTML/CSV, and cannot place a work in today's shortlist.

### Tasks, selection and drafts

A `task` adds `roundId`, `workId`, stable `taskId`, `kind: revisit|backfill`, `status: pending|done|cancelled`, `reason`, and `dueAt` (nullable for backfill). Revisit tasks also reference `baselineObservationId`; due time must be at least the configured interval after that saved like observation. Both the baseline and the due-time like reading must be available (exact or rounded); an unavailable reading keeps the revisit pending. The revisit baseline and deadline remain immutable across revisions (equivalent timezone offsets are accepted); create a new task ID to reschedule. Cancelling a task does not recheck its baseline files, so a task whose evidence was lost can still be closed. Marking a revisit done requires a later saved like observation at/after its original due time. Updating a task appends a new event with the same `taskId`. A revisit cannot be marked done, and a done revisit reopens with `baselineUnavailable: true`, when its baseline has been corrected to an unavailable reading. Completion checks the standing correction of the baseline and that correction's files, not the superseded original. If the reading that completed a revisit is later corrected to unavailable or excluded, the snapshot reports that task as `status: pending` with `reopened: true` and `recordedStatus: done`. Status exposes due tasks; it does not run a scheduler. A pending task on a work the user rejected is reported with `suppressed: true` and is never due; cancel it when convenient.

A `decision` adds `workId`, `decision: selected|watch|rejected`, `reason` and `userRequest` preserving the real user instruction. Never fabricate a selection from a model's shortlist. `watch` removes the work from the priority shortlist; `rejected` removes it from both shortlist and watchlist while retaining its materials and task history.

A `draft` adds `workId`, `selectionEventId`, `reviewId`, `status: draft`, `briefPath`, `scriptPath`, `evidencePath`. All three files must already exist. The helper rejects registration unless the latest user decision selects that work and `reviewId` names the newest review of that work, which must still be supported by intact files. If the newest review has lost support, record a new review first; an older review is never used in its place. After a correction, reread the latest review and update the new draft; do not use a superseded review. Historical drafts retain their original review IDs and can be replayed unchanged. Hashes protect saved draft revisions. The helper records drafts generated by the agent; it does not generate text or mark it published. A later rejection preserves historical drafts while preventing new ones.

The optional `hashes` field must be a JSON object when supplied, including when empty; arrays, null and primitives are rejected before saving. Omit it to let the helper calculate all three hashes, or supply existing hashes to verify them.

Brief, script and evidence paths must resolve to three different files, separate from every registered capture asset; aliases and hard links do not create separate documents or turn raw sources into drafts. Historical draft hash protection also compares resolved file identities, so an alternative spelling cannot overwrite an earlier registered document. Missing unrelated old drafts do not block new draft files; their original paths remain reserved and full integrity checks continue reporting their loss.

Separation is bidirectional: later captures cannot register a prior draft component or its file aliases as raw evidence. Legacy assets first registered after the same file became a draft remain in history but do not supply materials, observations, substantive-read eligibility or reviews.

Historical drafts are revalidated against their event prefixes without modifying records. A draft file edited after registration keeps its links in the dashboard with a note that the edit is unregistered, a missing draft file is reported without links, and a draft whose review lost support keeps its links with a note to recapture evidence and record a new review; save edits as new files and register a new revision to keep them. A draft whose review has lost support reports that review's problem as its gap. Only valid entries appear in `drafts` and generated-document links; `draftHistory` preserves all revisions and `draftGaps` records excluded entries in HTML/CSV. Programmatic callers must pass the store as the third `snapshot(events, now, store)` argument to verify draft files; without it, drafts remain unverified history. CLI status/render already supply that path. Output protection still covers every registered historical draft, including excluded ones.

## Limits

The helper validates structure, identity, file presence/hashes, reference integrity and arithmetic. Journal files are append-only through the helper but not tamper-evident: a manual edit to an event file is not detected. It cannot determine whether a screenshot really contains a work, an image was actually read, a source claim is true, a userRequest is authentic or a transcript is complete. The browser collector and reviewer must verify those facts. Synthetic tests do not establish live platform capability.
